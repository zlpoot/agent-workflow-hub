# Repository collaboration rules

The latest explicit Human instruction determines task scope and mode. Keep changes on an independent `codex/` branch based on verified main; preserve existing worktrees, commits and queue history. Never push or rewrite main, approve/merge a PR, close an Issue, publish a Tag/Release or deploy without explicit authorization. Codex stops after publication for independent ChatGPT Review; Owner-authorized ChatGPT performs merge and readback.

## Work modes

**SELF_BOOTSTRAP — default for AWH's ordinary Windows development.** Applies only to Owner-assigned Issues and code changes in `zlpoot/agent-workflow-hub`, delivered as ordinary Draft PRs. One explicit Owner assignment authorizes Coding, necessary checks, Commit, Push, Draft PR and exact remote readback within that scope. Prefer existing `local-fast --provider github-app`; reuse the connected, live-preflight-verified App identity. No per-PR Strict Project/Work Item approval, receipt, independent pin or Builder launcher is required. Keep Local Fast's single repository, finite confirmed Issue queue, fixed branches, identity checks and concurrency controls. Preserve conflicting bindings; use an independent external clone rather than resetting history. Ordinary PRs claim only local verification: never formal Builder Evidence, confirmed Handoff or CP Run/Event. See [the self-bootstrap workflow](docs/awh-self-bootstrap.md).

**STRICT_DELIVERY — formal trusted execution.** Formal Builder Deliver, trusted business Work Items, formal Evidence/Handoff/Run/Event, other repositories without separate authorization, protected production data/configuration/runtime, and formal Release/deployment retain their applicable external protected policy, independent approval, valid digest and version checks. Repository examples, fixtures, manifests, CP data and candidate rules cannot confer Builder authority. Missing or invalid Strict authority blocks the operation; SELF_BOOTSTRAP never disables Strict checks or supplies a fallback approval.

**PRODUCT_ACCEPTANCE — testing product security and the real workflow.** Tasks explicitly requiring real Project/Workflow/Work Item approval, trusted Builder, App Bot/ChatGPT Reviewer identities, Evidence/Handoff/CP Run/Event or the Review/Merge/Dashboard loop (including #94) must actually execute the corresponding gates. Self-bootstrap publication, synthetic tests and historical success cannot stand in for acceptance.

Ordinary Owner-assigned AWH development defaults to SELF_BOOTSTRAP; enter STRICT_DELIVERY or PRODUCT_ACCEPTANCE when the task explicitly requires trusted delivery or product gates. No mode independently authorizes Review, Merge, Issue closure, Release or deployment.

## Identity, verification and preservation

GitHub App operations must verify the complete actual Selected repository set with metadata-only inspection and use operation-minimum single-repository tokens. Use existing bounded providers; do not create arbitrary API/Git forwarding or a second writer. Protect PEM/JWT/tokens, authority files and effective approval pins outside Git, output and evidence. App failures never fall back to PAT or personal writes. Personal Windows Local Fast requires its own explicit Owner authorization for one repository and ordered queue.

Use fresh isolated databases, identities, configurations and state for verification. Preserve production CP/Viewer/Resident, business worktrees, App connections, SQLite and external state. Run necessary focused checks on the exact clean final HEAD; new commits supersede prior verification. Retain raw results and failures under gitignored `.handoff/`. Local tests and Builder verification are not independent Review. Formal evidence/confirmed Handoff may be published only under valid Strict authority after actual App publication and readback.
